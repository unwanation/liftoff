# `lof expose`: локальный порт в сети

`lof expose <PORT>` открывает порт машины разработчика в сеть через
сервер liftoff: туннель от демона до `localhost:<PORT>`. Проект не
нужен — это отдельная утилита, как ngrok или portless: приложение
запускается как обычно (`npm run dev`), `lof expose` только даёт ему
адрес. Код: `crates/liftoff/src/commands/expose.rs` (CLI),
`crates/tunnel` (протокол), `crates/rest/src/routes/tunnel.rs`
(upgrade), `crates/liftoffd/src/listeners/tunnel.rs` и `tunnels.rs`
(демон), `liftoff_core::service::TunnelsService` и `liftoff_core::expose`
(правила).

```sh
npm run dev               # приложение на localhost:3000, как всегда
lof expose 3000           # адрес и ссылка входа; Ctrl-C снимает адрес
lof expose 3000 --share   # адрес открыт всем, без входа
lof secret pull --write   # секреты environment в .env.<env> (0600)
```

## Адрес

Все адреса — под зоной `localhost.<base>`:

- `lof expose` на машине самого демона — `https://<port>.localhost.<base>`
  (`3000.localhost.example.com`). Порт сервера принадлежит первому, кто
  его открыл: тот же порт другого пользователя — `409`;
- с любой другой машины — `https://<login>-<id>.localhost.<base>`
  (`alice-3f9a1c2b.localhost.example.com`): логин (в нижнем регистре,
  всё, что не буква и не цифра, — `-`) и 8 hex-цифр SHA-256 от id
  пользователя и порта. Адрес постоянен от запуска к запуску, у каждого
  пользователя и порта свой и ничего не говорит о порте.

«На машине демона» решает демон: адрес клиента — loopback или
`public_ip` сервера. Адрес клиента — пир соединения, а для запроса
локального Caddy — последний адрес `X-Forwarded-For`, который Caddy
ставит сам. Ошибиться в эту сторону безопасно: в худшем случае адрес
будет вида `<login>-<id>`.

DNS: каждый адрес — managed-домен (хук `domain_created`, то есть
запись у модуля `dns.*`). Без модуля DNS нужна запись
`*.localhost.<base>` на сервер: wildcard `*.<base>` второй уровень не
покрывает. Сертификат Caddy получает на каждый адрес (ACME). С
`--proxied` Cloudflare (оранжевое облако) бесплатный сертификат не
покрывает `*.localhost.<base>`: эти записи должны быть DNS-only.

Туннели не принадлежат проекту пользователя: они живут в собственном
проекте установки `localhost` (репозиторий `liftoff/localhost` на хосте
`<base>`, которого нет ни на одном форже), который создаётся при первом
`lof expose` и не показывается ни в одном списке. Проект пользователя с
именем `localhost` создать нельзя, а `localhost` — зарезервированная
метка managed-доменов. Внешний домен под `<base>` любой глубины
(`a.localhost.<base>`) — ошибка валидации.

## Как идёт запрос

CLI открывает `wss://<api>/api/v1/tunnel` с `cli`-сессией (`lof
login`), портом в `X-Liftoff-Expose` и, с `--share`, `X-Liftoff-Share:
1`. Демон находит или создаёт туннель пользователя для порта
(environment kind `tunnel`, владелец — вы), добавляет ему managed-домен
и привязку, отвечает `101` с `X-Liftoff-Address` и, для приватного,
`X-Liftoff-Login-Url`; после рукопожатия (`Hello` с обеих сторон) —
`running` и маршрут Caddy → tunnel-listener (`[tunnel] bind`).

CLI печатает в stdout один раз за запуск, после первого соединения,
адрес и для приватного туннеля — ссылку входа. Запрос идёт: браузер →
Caddy → tunnel-listener → поток `yamux` внутри WebSocket →
`127.0.0.1:<PORT>`, а если там никто не слушает — `[::1]:<PORT>` (Vite
на свежем Node слушает `localhost` только по IPv6). WebSocket самого
приложения (HMR Vite, webpack-dev-server, Next.js) проходит через
туннель как есть: правки видны в браузере без перезагрузки страницы.
Если на порте при старте никто не слушает, CLI говорит это один раз в
stderr; адрес отвечает `502`, пока приложение не поднимется.

Что видит приложение: `Host: localhost` (dev-серверы отказывают хостам,
которых не знают: `server.allowedHosts` Vite, проверка хоста
webpack-dev-server; адрес — в `X-Forwarded-Host`), запрос без cookie
`__Host-liftoff*`, без `Authorization` с токеном liftoff, без
`X-Forwarded-*`, `Forwarded` и `X-Liftoff-*` браузера; listener ставит
свои `X-Forwarded-For` (адрес клиента, который записал локальный
Caddy), `X-Forwarded-Proto: https`, `X-Forwarded-Host: <адрес>` и для
пропущенного человека `X-Liftoff-User`, `X-Liftoff-Email`. Пути
`/.liftoff/*` принадлежат liftoff и до приложения не доходят.

## Приватность и share

Туннель `private`, пока `lof expose` не запущен с `--share`; запуск
без `--share` делает его снова приватным. Приватный адрес открыт только
владельцу туннеля и админу:

- с сессией этого хоста (cookie `__Host-liftoff_gate`) или с
  `cli`-сессией в `Authorization: Bearer` (`curl -H "Authorization:
  Bearer …"`);
- с модулем `oidc` вход — single sign-on провайдера (страница модуля);
- с модулем `tenants` никто, кроме владельца и админа: туннели не в
  тенанте, и хук `gate` никого больше не пропускает.

Браузер без сессии получает `302` на вход, JSON-клиент (`Accept:
application/json`) — `401`, сессия того, кому нельзя, — `403` (HTML-страница
отказа). Проверка — до первого байта в туннель.

**Вход по ссылке** (без модуля `oidc`). Ссылка, которую печатает `lof
expose`, — `https://<api>/api/v1/auth/links/lfl_…`: одноразовая, 10
минут, только для этого туннеля. Открытая в браузере, она создаёт
сессию `browser` на 24 часа (cookie API-хоста `__Host-liftoff_session`)
и сразу передаёт её на адрес одноразовым кодом: `302` на
`https://<адрес>/.liftoff/callback?code=lfc_…`, listener гасит код,
ставит cookie `__Host-liftoff_gate` и возвращает на `/`. Браузер,
пришедший на приватный адрес без сессии, попадает на страницу входа
`https://<api>/login?host=&rd=`. При переподключениях ссылка не
печатается снова: новая — при следующем `lof expose`.

## Права

Без модулей `lof expose` может только админ (единственный пользователь
single-user режима — админ). Модуль `tenants` (0.3.0) открывает действие
`tunnel.expose` всем пользователям. Хук `authorize` спрашивается один
раз, о ресурсе `admin` (установка целиком).

## Обрыв, `Ctrl-C`, offline

- Keepalive — пинги клиента раз в 15 секунд; сервер рвёт соединение без
  кадров клиента дольше 45 секунд, клиент — без кадров сервера дольше
  трёх интервалов.
- Обрыв: CLI пишет в stderr «the tunnel connection broke; reconnecting»
  и переподключается с backoff (1 секунда, удвоение, потолок 60
  секунд), по возвращении — «the tunnel is back». Через
  `tunnel.offline_after` (30 секунд) без клиента туннель становится
  `offline`, и Caddy отдаёт `503` «dev offline».
- `Ctrl-C` (и `SIGTERM`, `SIGHUP`): CLI шлёт кадр `Shutdown` — туннель
  `offline` и маршрут снимается сразу; выход 130.
- Второй `lof expose` того же пользователя и порта вытесняет первый
  (кадр `Evicted`): первый пишет об этом и завершается с 1.
- Отказ upgrade окончательный, выход 1: `401` (сессии нет, она
  истекла) — «log in again with `lof login`»; `403` (не `cli`-сессия,
  deploy-токен, `authorize` отказал); `409` (порт сервера другого
  пользователя) — с причиной сервера.
- Без сервера (локальный режим) открывать не через что: выход 78 и
  подсказка `lof login <url>`.
- Старт демона делает все туннели `offline`.

## Секреты

`lof dev` больше нет, и секреты environment в процесс никто не
подставляет. `lof secret pull --write` пишет их в `.env.<env>` в корне
рабочего дерева (`--env`, иначе `.liftoff`, иначе `prod`): файл
заменяется целиком, права `0600`, в stdout — путь, значения — только в
файле. Держите его вне git (`.gitignore`). Без сервера — из локального
хранилища.

## Лимиты демона

| Ключ `[tunnel]` | По умолчанию | Что ограничивает |
|---|---|---|
| `bind` | `127.0.0.1:7004` | адрес tunnel-listener'а (только loopback) |
| `max_streams` | `64` | одновременные запросы одного туннеля; лишний — `503` |
| `offline_after` | `30s` | сколько потерянный туннель ждёт клиента до `offline` |
| `bandwidth` | `{ bytes_per_second = 10485760, burst = 1048576 }` | полосу туннеля на оба направления (токен-бакет, переживает переподключение) |

Сообщение WebSocket — не больше 256 КиБ с обеих сторон; окно `yamux` —
256 КиБ на поток `max_streams` с запасом в четверть, так что память
демона на туннель ограничена.

Каждый туннель занимает порт `[domains] port_range` в своей привязке,
хотя его никто не слушает (колонки портов привязки `NOT NULL`). За
внешним прокси (`tls = "edge"`) idle-таймауты на пути WebSocket должны
быть длиннее интервала keepalive: короткий `read_timeout` рвал бы
туннель.
